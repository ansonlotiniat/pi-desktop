# Pi Desktop Knowledge Base

Last updated: 2026-08-19

## Reframed goal

Build a simple, clean, macOS-only desktop GUI for the official Pi coding agent (`pi.dev`). The desktop app should preserve Pi's core behavior and philosophy, remain decoupled enough for the Pi kernel to update independently, and use macOS-specific choices to keep startup, memory use, and interaction latency low.

## Confirmed product decisions

- Product boundary: Pi Desktop is only a GUI/control plane. Pi remains the sole agent runtime and source of truth; the app must not reproduce or replace kernel behavior.
- Kernel boundary: launch one user-installed Pi process in fullscreen native TUI mode under a real PTY. Load a small Desktop-owned bridge explicitly through Pi's public ExtensionAPI; do not import Pi internals or run a second agent/session engine.
- Desktop shell: Tauri 2 with a React/TypeScript UI, using the native macOS WebKit runtime rather than bundling Chromium.
- Credentials: v1 stores API keys together with provider configuration in an app-owned JSON file, per user choice. The file must be private (`0600`), excluded from logs, and values masked in UI. Keychain migration remains a later hardening option.
- Feature parity: normal GUI chat/state uses the public ExtensionAPI sideband. Desktop owns a metadata-only composer palette for discovering and inserting slash commands, prompt templates, and `/skill:<name>` invocations. Pi remains the sole executor; selectors, login flows, command handlers, and extension-defined custom components stay inside Pi's real TUI.
- Kernel distribution: the app never bundles, downloads, embeds, or silently substitutes Pi. It launches a user-installed or explicitly selected external executable, allowing Pi to update independently.
- Pi is the only automatic-discovery target. Oh My Pi (OMP) may be used as an explicitly configured compatible executable, but is never an implicit fallback or a source of product-specific GUI concepts.
- Connection truth: spawning a process is not enough. The app reports Connected only after the versioned bridge handshake includes authoritative state read from Pi's public session context.
- Session truth: Pi owns session persistence and mutations. The GUI does not keep a separate history database, parse session JSONL, use `--no-session`, or use a private `--session-dir`. Desktop may present Pi-owned history metadata using Pi's public top-level `SessionManager.listAll()` export and switch the resident runtime through public `ExtensionCommandContext.switchSession()`; Pi still performs the actual session transition and remains authoritative.
- Resident native TUI: the same Pi process, PTY, agent runtime, and active session remain alive throughout normal chat, native commands, new-session, and history switching. The terminal renderer is parked offscreen during normal GUI chat and revealed only after a submitted command needs Pi's interactive surface; reveal/hide never performs resume, patch, or process replacement. Explicitly choosing a brand-new launch workspace is the one controlled restart boundary.
- UI direction: ultra-minimal dark terminal, with a centered 704 px conversation column, a floating pill composer, and session/inspector surfaces opened as overlay drawers. Typing `/` opens a Desktop-native, cursor-aware palette above the composer; it live-filters without replacing the editor, labels Pi/Extension/Prompt/Skill provenance, and supports keyboard or pointer insertion. Use the native macOS system font stack with integer weights, automatic WebKit smoothing, optical sizing, and no synthetic fonts. Keep normal UI labels at 13 px or larger, conversation/composer text at 16 px, and selected/focus indicators at 2–3 px so text and highlights remain legible without forced thin antialiasing.
- Extensibility intent: users may ask an agent to author complete Desktop sidebar applications such as code review, diff inspection, or PR management. Each feature may own its entire UI, business logic, service/API integration, state, and authentication flow; it is not limited to enabling or composing Desktop-provided domain functions. The Desktop team provides only a small stable host/bridge, optional SDK conveniences, and explicit loading/management rather than implementing or pre-installing those tools.
- Official-plugin distribution: the app binary contains versioned Code Review, Code Diff, PR Workspace, and Project Map packs plus catalog metadata, but they are not installed or discovered as active features by default. Only an explicit **Install** click copies one to `~/.pi-desktop/features/`; later versions show **Update** both in navigation and on the active feature header. Pi Desktop updates only owned packs or recognized legacy starter copies, preserves a legacy backup, and refuses to overwrite a custom same-ID plugin. No network download or silent installation occurs.
- Source repository: the project is maintained in the public GitHub repository `https://github.com/ansonlotiniat/pi-desktop`, with `main` as the default branch.

## Upstream facts and sources

- Official site: <https://pi.dev/>.
- Official repository moved to `earendil-works/pi`: <https://github.com/earendil-works/pi>.

CLI `--approve` / `--no-approve` controls project-resource trust for that launch, not approval of individual shell or file operations.
- Pi's public `tool_call` extension hook runs before tool execution and can return a documented block result. Desktop may therefore offer an explicit extension-level approval gate without patching or emulating the kernel, while leaving **Pi default** byte-for-byte aligned with native behavior.
- RPC documentation: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md>.
- Pi exposes a documented JSONL RPC mode covering prompt/steer/follow-up/abort, messages, models, thinking, sessions, tree/fork/clone, compaction, bash, export, and extension UI events.
- New CBOR client/server packages are explicitly experimental, so they are not the v1 contract.
- Confidence: high for all facts above; read from upstream documentation/package metadata on 2026-08-10.
- Upstream `main` inspected on 2026-08-12 already contains an experimental multi-client direction: separate `@earendil-works/pi-protocol`, `@earendil-works/pi-server`, and `@earendil-works/pi-client` packages; framed CBOR protocol v1; Unix-domain socket transport; authoritative server/session snapshots; attach/detach; and shared/exclusive client-side session leases.
- `@earendil-works/pi-coding-agent/client` already exposes `RemoteSession`, and the experimental CLI grammar already reserves `pi --listen`, `pi server`, and `pi client --connect`. These composition commands are not wired into the released CLI path yet.
- The current server README explicitly says it does not provide a standalone CLI or coding-agent service. Merged PR #7614 deliberately removed the legacy child-process server without adding the new coding-agent service. This is an active upstream seam, not a reason for Desktop to invent a competing app-server protocol.
- The protocol is explicitly experimental and currently covers normalized session/model/transcript operations, not arbitrary Pi extension TUI. The native-extension-preserving route is therefore a dual-host process: keep the ordinary Pi InteractiveMode attached to Desktop's PTY while the same process exposes semantic state through the experimental Unix-socket server.
- Upstream contribution policy requires a concise contribution proposal and a maintainer `lgtm` before a new contributor opens a PR. The locally authenticated `ansonlotiniat` account is not presently listed in `.github/APPROVED_CONTRIBUTORS`.

### Public Pi GUI slash-command survey (2026-08-12)

- The dominant external-kernel pattern is `get_commands` -> GUI autocomplete/palette -> submit the literal `/command ...` through RPC `prompt`. Host-specific built-ins such as `/model`, `/resume`, or `/tree` are commonly intercepted and redrawn as GUI panels. Emacs `pi-coding-agent`, cmux `agent-chat`, Bill-vvv's Pi GUI, and Claudian all follow variants of this pattern.
- External-RPC clients implement only Pi's serializable extension-UI subset (`select`, `confirm`, `input`, `editor`, notifications/status/widgets) and cancel, omit, or cannot render arbitrary `ctx.ui.custom()` terminal components. This provides useful command routing, but not universal slash/TUI compatibility.
- SDK-embedded Electron clients (`minghinmatthewlam/pi-gui` and `justhil/pi-app`) inspect `AgentSession` internals and build their own UI bridges. They still hardcode built-ins and leave arbitrary custom terminal UI unsupported, while coupling their release to Pi's package internals; this does not satisfy Desktop's external-kernel boundary.
- `agegr/pi-web` is the closest public attempt at generic custom UI: it embeds Pi's SDK, invokes extension TUI component factories against a fake/headless TUI, serializes rendered terminal lines to the browser, and forwards key input back to the component. It is not a real PTY, leaves parts of the terminal/UI contract unimplemented, and effectively rehosts Pi's internal TUI ABI.
- No inspected public client kept one official external Pi InteractiveMode alive in a real PTY while also exposing semantic GUI state. Pi Desktop now implements that public-ExtensionAPI sideband pattern locally; an upstream dual-host composition seam remains relevant only if Desktop later needs the complete official RPC surface simultaneously with native InteractiveMode.

## Architecture

```text
React UI in macOS WKWebView
   +-- normal GUI chat/state
   +-- resident xterm surface (parked or visible)
              |
        Tauri invoke/events
              |
    Rust supervisor + PTY + Unix socket
       +-- raw VT bytes <------> one external `pi --tui-mode fullscreen`
       +-- JSONL sideband <----> explicitly loaded Desktop bridge extension
                                      [public ExtensionAPI only]
```

- The UI never imports Pi internals.
- The Rust adapter owns one child lifetime, the real PTY byte stream, Unix-socket framing/request correlation, and event forwarding. It never interprets VT screen content.
- `@xterm/xterm` is only the resident VT terminal renderer. It mounts before Connect and remains laid out offscreen so terminal capability queries are answered even when the TUI is visually hidden; revealing it does not start another Pi.
- The Desktop-owned bridge is written to the app cache and passed with `--extension` for this process only. It is not installed into the user's Pi configuration. It exposes snapshots/events, prompt/steer/follow-up, abort, model/thinking setters, session naming, metadata-only history discovery, an opaque-token resident-session switch, and an optional pre-execution approval gate using only public Pi exports and ExtensionAPI hooks.
- The sideband is deliberately narrower than official RPC. Desktop redraws the history browser and `/resume` entry, but Pi still lists/persists/switches the underlying sessions. Other slash commands, provider login, arbitrary extension UI, tree/fork/clone, and exports remain native TUI operations.
- Pi session replacement may reload the bridge extension and briefly reconnect the socket, but the outer Pi process and PTY remain alive. Each reconnect sends a fresh authoritative state snapshot; Desktop never replays or patches a session.
- Kernel path is configurable. Discovery prefers an explicit path and then an external `pi` on PATH or known macOS installation locations, including Homebrew, local/bun/Volta/pnpm paths and version-managed FNM, NVM, nodenv, asdf, and mise installations. Source-tree binaries, app resources, and OMP are not automatic candidates.
- Finder-launched apps do not inherit the interactive Terminal PATH. When Pi is discovered, prepend its own bin directory to the kernel child PATH so Node-based `#!/usr/bin/env node` launchers can resolve the adjacent version-managed Node runtime.
- Finder-launched apps also do not inherit Terminal proxy variables. On macOS, map active HTTP/HTTPS proxy settings from `scutil --proxy` into upper- and lower-case proxy environment variables for the Pi child, while preserving any proxy environment explicitly inherited by the app.
- API provider metadata is written as Pi-compatible model configuration, while app-only state stays in the app config directory.
- Session files remain in Pi's normal project-scoped location under `~/.pi/agent/sessions`; `pi -r` from the same working directory can find sessions created through the GUI.
- Pi 0.84.1 does not expose list-all history through official RPC or passive ExtensionAPI state, but the package's public top-level export includes `SessionManager.listAll()`. The bridge may call that public metadata API and return only path/id/cwd/name/parent/timestamps/message count/first message; Desktop must not read or reinterpret JSONL itself. Treat this as a public-package compatibility seam and keep future diagnostics explicit.
- **Browse Pi history** and `/resume [query]` now open a Desktop-drawn metadata browser grouped by Pi-reported `cwd`. Folder expansion state is Desktop presentation state only. Selecting an entry submits a one-use opaque internal extension command to the parked PTY; the handler calls public `ctx.switchSession(path)`, so the same Pi PID/runtime performs the transition and emits a fresh authoritative state snapshot.
- Switching to a historical session from another folder keeps the same resident Pi process and adopts that session's Pi-reported `cwd`. Choosing a brand-new workspace folder is different: initial working directory is launch-scoped, so the app persists the selection, stops the current external Pi, waits for its PTY to finish, and starts the same configured external executable in the selected folder.

### Implemented resident TUI + non-kernel bridge

Adopted on 2026-08-12. This does not patch, embed, or replace Pi:

```text
Pi Desktop
  +-- PTY bytes <----------------------> one external pi InteractiveMode
  +-- tiny JSONL Unix-socket sideband <-> Desktop bridge extension loaded with -e
                                                |
                                     official ExtensionAPI only
```

- Start the user-installed Pi once in native TUI mode and keep that process/PTY alive throughout the selected launch workspace. Hide or reveal the terminal surface without replacing the Pi process. New sessions and historical session switches, including sessions whose Pi-reported cwd differs, preserve the same process; only an explicit brand-new workspace selection restarts it.
- Load a Desktop-owned bridge extension explicitly with `-e`; do not install it into the user's Pi settings. Its only command is an internal, opaque-token session-switch bridge that is filtered from Desktop command discovery and delegates directly to public `ctx.switchSession()`. The official API also exposes read-only session state, current model/thinking/idle state, message/tool/model/thinking/session lifecycle events, `sendUserMessage()`, and abort. The extension may connect to a Desktop-owned Unix socket during `session_start` and close/reconnect on `session_shutdown` exactly as Pi's documented lifecycle requires.
- Keep the sideband deliberately narrower than RPC: handshake/capabilities, authoritative snapshots/events, normal prompt/steer/follow-up, abort, Pi-owned metadata history, and resident session switching. Other slash commands, model selectors, login flows, and arbitrary extension UI stay on the real PTY. Do not parse VT output or session JSONL, and do not import private paths or monkey-patch Pi internals.
- Session replacement reloads the extension instance but does not restart the Pi process. Desktop must accept a short sideband reconnect and replace its view from a fresh public-API snapshot.
- Public extension hooks do not expose a generic command/custom-component opened/closed lifecycle. Known operations can auto-collapse the embedded terminal from `model_select`, `thinking_level_select`, `session_start`, or `session_tree`; arbitrary extension TUI must remain visible until the user closes the terminal surface. Perfect universal auto-collapse would need a small upstream interactive-surface lifecycle hook, not a new kernel/server architecture.
- If Desktop later needs the complete official RPC command surface simultaneously with native InteractiveMode, an upstream dual-host composition point is still required. It is not required for the current GUI/state/message bridge.

### Candidate upstream-aligned runtime architecture

This is not yet an adopted implementation because the upstream interfaces are experimental and incomplete:

```text
Pi Desktop
  +-- PTY bytes <----------------> one external pi InteractiveMode
  +-- framed CBOR over Unix socket <-> PiServer adapter
                                             |
                                  same AgentSessionRuntime
```

- Spawn one user-installed `pi --listen unix://...` process in a PTY and never replace it when entering slash/TUI mode. The native Pi TUI remains the only executor and renderer for prompts, slash commands, extension commands, selectors, and custom terminal components; Desktop only reveals or resizes its terminal surface.
- Use the socket connection as the semantic observation/control plane for transcript, model, thinking, session metadata, and events. Do not parse terminal output into state and do not recreate extension UI.
- The missing upstream composition is a coding-agent `PiServerService` adapter over the already-running `AgentSessionRuntime`, plus an active-session transition signal when `/new`, `/resume`, `/fork`, `/clone`, or import replaces the runtime session. The adapter must borrow the TUI-owned runtime rather than dispose or recreate it when a remote observer detaches.
- Keep this behind the existing experimental CLI surface so ordinary `pi` behavior is byte-for-byte unchanged when `--listen` is absent. Until upstream accepts and releases it, Desktop's current public-ExtensionAPI sideband remains the implementation.

## Implemented Feature Host v1 architecture

- Do not create a second agent kernel or reproduce Pi tools/session/model behavior. Official Pi skills, TypeScript extensions, prompt templates, themes, and packages remain the agent-runtime extension mechanism.
- A separate, deliberately small Desktop Feature Host is appropriate for agent-authored full GUI applications. It loads and connects feature code but is not another agent runtime; any LLM/agent operation still goes through the official Pi kernel.
- Feature Host code is split into Rust discovery/process/storage modules, a thin Tauri transport, an injected browser SDK, an isolated frame, and host navigation/management UI. The older chat path in `usePiDesktop.ts` still needs its separate protocol/reducer/controller refactor.
- Slash command discovery is shell UI, not Feature Host UI. Desktop merges a small current built-in presentation catalog with Pi's public `get_commands` metadata for extensions, prompt templates, and skills; it only inserts invocations into the composer. Submitting a command still opens the official Pi TUI in the resident PTY, so command execution and arbitrary `ctx.ui.custom()` components remain Pi-owned. Public `get_commands` intentionally omits built-ins, so new unknown built-ins remain executable when typed but cannot be auto-suggested until Pi exposes built-in metadata or Desktop updates its presentation list.
- A Desktop feature pack should have a versioned manifest, a complete frontend entry (built HTML/JS; React/Vue/vanilla are feature choices), an optional separate service process using a small JSONL/JSON-RPC contract, and an optional companion Pi skill/extension. Give agents a standalone scaffold and SDK docs instead of the full Desktop repository.
- Load each feature frontend in an isolated child webview/frame rather than importing its React/components into the main application bundle. Isolation is primarily a compatibility boundary: feature dependencies, CSS, routing, and failures must not couple to or restyle the host app.
- The app owns only the Codex-style navigation shell. A feature manifest registers its sidebar identity and frontend entry; after navigation, the entire feature surface belongs to that feature. Optional host UI components/theme tokens may help consistency but cannot be mandatory or limit what the agent can build.
- The versioned host bridge stays narrow: host/workspace context, messaging to a feature service, app storage, external-browser opening, Pi RPC requests, and Pi/service events. A feature service may perform deterministic git/API/domain operations without model tokens; agent work must be requested through Pi.
- Feature-specific authentication is owned by the feature. It may use an existing authenticated CLI, render its own token/account UI, or drive OAuth through an external browser plus a service-owned localhost callback. Desktop supplies storage and transport primitives, not provider-specific auth screens or logic.
- Trusted local feature services run with the user's local authority, like Pi extensions. Do not invent a misleading heavy permission system; keep enable/disable, source path, and explicit installation visible.
- Project features are discovered under `<workspace>/.pi-desktop/features/`; global features are discovered under `~/.pi-desktop/features/`. Desktop lists and reloads them but never downloads or silently installs them. A project feature overrides a global feature with the same ID.
- The host exposes four versioned app-bundled official packs in the Plugins catalog. A pack remains inactive metadata until the user clicks **Install**; installation atomically writes the complete feature into the global discovery directory. Code Review and Code Diff share a deterministic Git workbench. PR Workspace reuses the user's authenticated `gh` CLI for PR lists, checks, details, changed files, and per-file patches. Project Map locally scans Git-aware files, languages, modules, entry points, inferred cross-module imports, and source previews. No official pack invokes a model until the user explicitly chooses an **Ask Pi** or review action.
- Feature frontend API v1 is a self-contained HTML entry loaded into a sandboxed `srcdoc` frame; React/Vue/Svelte/vanilla are build-time choices owned by the feature. The host injects `window.piDesktop` before feature scripts run.
- An optional long-lived service is declared as a command plus arguments and communicates through strict LF-delimited JSONL request/response/event records. `node` resolves beside the configured/running Pi executable first, then PATH; other commands and explicit paths are allowed. The service inherits the workspace and mapped macOS proxy environment.
- Feature JSON storage is namespaced by feature ID in an app-owned `0600` file. The feature decides which values represent auth/state and sends anything needed by its service through the bridge rather than process arguments.
- Keep two authentication domains separate. An extension may own service-specific setup through generic UI interactions, but model-provider OAuth/login belongs to Pi. As of 2026-08-12, the documented RPC command set has no login/auth command even though custom providers can integrate with Pi's terminal `/login`; do not work around this by writing Pi's `auth.json` directly.
- The current Desktop-owned provider/API-key editor is a v1 compatibility convenience, not the foundation for a general plugin authentication framework.

## Implemented AI feature-authoring support

- The app bundles the self-contained `pi-desktop-feature-builder` skill with its version-matched Feature Host reference, TypeScript declarations, manifest schema, and copyable complete feature template. Progressive disclosure keeps only its name/description in ordinary agent context.
- The Plugins screen exposes explicit **Enable authoring**, **Update**, and **Remove** controls. Enabling copies only this Pi Desktop-owned skill to `~/.agents/skills/pi-desktop-feature-builder`; it does not install a third-party plugin, dependency, Pi kernel, or model credential.
- A small owner/version marker controls updates and removal without hashes. A same-name unowned directory is reported as a custom skill and is never overwritten or removed.
- The drag-and-drop `.app` has no install hook, so authoring remains opt-in inside the app. A future first-launch disclosure may link to the same controls, but must not silently broaden installation.
- A separate `pi-desktop-maintainer` skill remains deferred. Core app changes still require a source checkout and its `knowledge.md`; agents must never patch the signed installed `.app`.

## Proposed macOS distribution plan (awaiting implementation confirmation)

- Exclude the Mac App Store. The canonical consumer artifact should be one Developer ID-signed and Apple-notarized Apple Silicon DMG containing `Pi Desktop.app`; initially host that exact artifact on GitHub Releases and point the product website download button to it.
- Bundle first-party authoring skills inside the app through Tauri `bundle.resources`, so app and skill contract versions travel together. The current release carries `pi-desktop-feature-builder` under `Contents/Resources/resources/skills/`; explicit in-app enable/update copies the owned skill to `~/.agents/skills/`.
- Keep skill onboarding inside the app rather than implementing separate DMG, Homebrew, and shell-script install logic. Every delivery channel should install the same app artifact, and the app should expose repair/update/remove controls plus the installed skill version in Settings.
- Treat a Homebrew Cask in a project-owned tap as a later developer convenience, not the primary channel. A versioned Cask normally requires a `sha256` stanza; under the current project rule prohibiting SHA/digest work, defer this channel unless that policy is explicitly changed. Do not use Cask `postflight` to install user skills.
- Do not make `curl | sh` canonical. If added later for advanced users, publish a short inspectable wrapper that fetches/opens the same notarized DMG and leaves first-launch skill onboarding to the app. Reserve notarized PKG distribution for enterprise/MDM needs and ZIP for fallback/nightly builds.
- Source basis reviewed 2026-08-12: Apple direct-distribution/Developer ID guidance, Tauri DMG/signing/resources documentation, and Homebrew Cask documentation.

## Key parameters

- Target OS: macOS only, Apple Silicon first.
- UI stack: React 19 + TypeScript + Vite inside Tauri 2.
- Rust minimum: whatever current Tauri 2 resolves; local toolchain is Rust 1.94.
- Local machine: macOS 26.3 arm64; Node 25.x; Swift 6.3.3.
- Official Pi is installed through FNM at `~/.local/share/fnm/node-versions/v25.9.0/installation/bin/pi`. OMP also exists at `~/.bun/bin/omp`, but automatic discovery deliberately ignores it.
- Build workflow: if disk space becomes insufficient, stop and ask the user before deleting artifacts, clearing caches, or redirecting output to another volume. This is enforced in the project `AGENTS.md`.

## Security and privacy boundaries

- Never include API keys in logs, process arguments, events, error messages, or frontend diagnostics.
- Credential JSON is app-owned and written with Unix mode `0600`.
- The v1 plaintext-at-rest choice is explicit and should be disclosed in settings.
- **Pi default** preserves Pi's native authority model: tools and extensions run as the current macOS user, with no fabricated sandbox or yolo label. The opt-in, process-scoped **Ask before actions** mode uses Pi's public `tool_call` hook: official read-only `read`, `grep`, `find`, and `ls` tools continue directly, while `bash` (including `cd`/`rg`), `write`, `edit`, and other/custom tools pause for a Desktop-rendered **Allow once** or **Deny** decision. This gate is an extension policy, not a kernel capability or OS sandbox; trusted installed Feature Host services remain separately user-authorized local code.

## Open questions

- Product name and app icon are not final; use `Pi Desktop` as a working name.
- Official RPC still lacks a list-all historical-session command. The current implementation uses Pi's public package-level `SessionManager.listAll()` export, so future Pi compatibility diagnostics should report if that public seam changes rather than falling back to JSONL parsing.
- OMP compatibility needs a protocol probe after the local Bun/OMP installation is repaired and only matters for explicitly configured OMP paths.
- Whether to request/implement upstream Pi RPC support for provider login plus secret/password input before promising fully GUI-driven authentication for agent-authored extensions.
- Whether the current Desktop-owned provider editor should be retained as a narrow fallback after official RPC authentication becomes available.
- Whether Feature Host API v2 needs a local multi-asset URL protocol; v1 deliberately requires one self-contained HTML entry so arbitrary frontend dependencies remain isolated without coupling to the main Vite bundle.
- Whether a future host-level deep-link callback is useful for OAuth providers that cannot redirect to a service-owned localhost callback.
- Whether to add a first-launch shortcut to the existing opt-in authoring control. The implemented Plugins control remains explicit and reversible; do not make it default-on without a new product decision.
- Whether the initial public artifact remains Apple Silicon-only or also ships a Universal build.
- Developer ID/notarization credentials and the canonical GitHub Release repository still need to be configured before public distribution.
- Whether the no-SHA rule intentionally rules out a normal pinned-version Homebrew Cask; do not add or calculate a Cask checksum without explicit user approval.
- Public extension hooks do not expose a generic "interactive TUI surface opened/closed" event. Desktop therefore cannot safely auto-hide every unknown custom component; the user closes the terminal surface manually unless a known lifecycle event is available.
- Whether upstream wants `pi --listen` to dual-host the ordinary local InteractiveMode and a semantic Unix-socket server, or intends the local TUI eventually to become a client of a standalone server. Do not implement against this active experimental seam before a maintainer confirms the intended composition point.
